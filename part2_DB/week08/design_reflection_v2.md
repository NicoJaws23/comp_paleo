For me, some of the biggest revisions was the sheer number of tables I made to organize my data. I started with five tables and now have 8. When doing this assignment, I started from scratch to build something new that I felt would meet my goals. I ended up breaking my data down further than previously to ensure that small edits to one table do not cause significant changes to the rest of the database. These changes came from reflecting on all the data we currently have in the project database and trying to translate it into a new format that will be just as if not more effective. An initial change was just making my tables match names and keys already present in the standard database. I also started using surrogate keys to distinguish individual rows of focal data and gps points. Previously, this data did not have a single unique marker unless you look at the associated avistaje or observer sample ID and combined it with the data and time of each point. I felt this would make it easier to look up individual records once I start running analysis and creating an interactive platform for researchers. My field types, key choices, and relationships are pretty consistent with my first draft; however I did add some extra time fields to measure the durations of activities. 

One constraint I had a hard time with were those related to time. I really wanted a constraint which would detect when focal follows or avistajes exceeded 24 hours, indicating an observer did not properly record their start or end times. I originally wanted something that would first calculate the duration and then note if it was greater than 24 hours, but the method I found to calculate duration converted it to text. I chose to simply ensure that the value of end times was greater than that or start times, this should work the way I want it to. One constraint I can’t do with SQL is checking Spanish versus English language entries and converting entries from one to the other. Our team is made up of both English and Spanish speakers who may enter data (such as field notes or observer names) with characters not present in the opposite language (ex: ñ). SQL uses dynamic typing instead of rigid typing, so it can’t enforce set constraints for characters. Another thing SQL can’t enforce is overlapping time intervals. For example, a single observer should not have 2 focals or 2 avistajes with follow data happening at the same time. SQL can’t do this because it is reading each row individually, so it is not looking at multiple rows at the same time. 

When selecting candidate and eventual primary keys, I was sure, as the readings discuss, to establish ones which were not multipart fields, contained unique values, and would exclusively identify the value of each field within a given record. For example, observer_sample_id is the primary key for the observer_sample table. This unique string of letters and numbers (ex: OS12345) links to a specific observer (ex: Nico Jaworski), the date the observer was working (ex: 2026-06-07), and the gps used by the observer (ex: GPS PP19). This primary key can then connect to individual gps points and sightings of primate groups, indicating who saw the group, the date they saw them, and provided associated geospatial data of where the group was. When establishing relationships between tables, the books notes that one-to-many relationships are good for eliminating duplicate data and keeping redundant data to a minimum. When I created my tables I ran with this. I think of my tables in a Russian doll kind of way, each is a smaller/more specific version of the larger whole. Following this, I avoid redundant data by assigning each a linking ID. For example, observer_sample holds the name of the observer and date of fieldwork. This is linked to the avistaje and through avistajes to focal samples. Through this linkage, I do not have to constantly input the name of the observer and date of observations, instead it is all linked back to the observer_sample table through the observer_sample_id.
